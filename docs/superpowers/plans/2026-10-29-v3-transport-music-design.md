## 2. 四种模式的新定义

| 产品模式 | 后端/传输标识 | 默认部署条件 | 对 MC 连接的依赖 |
|---|---|---|---|
| A | TS3 / UDP | 客户端 SVC+teamspeak-svc，TS3 可达；MC 服务端无需本扩展/SVC | 手动 TS 目标独立于 MC 服务端推荐 |
| B | TS3 / **TS_MC_CHANNEL** | 当前 MC 服务端安装 teamspeak-svc，启用 TS 中继并能访问允许的 TS UDP；不要求 SVC 服务端或 TS 插件 | 绑定当前 MC 网络连接；MC 换服/断线使本中继失效 |
| C | SVC / UDP | MC 服务端 SVC，客户端 SVC；本扩展不改原生行为 | 由原 SVC 会话管理 |
| D | SVC / **SVC_MC_CHANNEL** | MC 服务端 SVC+teamspeak-svc，客户端支持该适配；不强制额外装 SVC-Extra | 绑定 MC 与 SVC 两种会话生命周期 |

`TS_TUNNEL_V1` 是独立的历史兼容传输，不等同 TS_MC_CHANNEL，不得把旧 `tcp=true` 一律重解释为新模式。以后迁移配置时保留来源和显式传输标识，旧端口/根秘密不能自动用于 MC 通道。

“服务端可选”针对基础 A/C；选择 B/D 时，相应中继或 SVC 服务端支持是该模式的必要条件。这不破坏纯客户端 A 的独立性。TS 服务器地址也不因中继绑定 MC 而被替换成 MC 地址。

## 3. P6：TS3 over Minecraft TCP 的建议技术契约

### 3.1 可复用基础与需要验证的地方

编写时 `TsTransport` 已支持完整 TS 数据报 send/receive/close，`Ts3Connection` 有传入 transport 的构造器，接收上限现用 4096 字节。适合在 transport 边界增加 MC 通道实现，而不是在 Minecraft 服务端再实例化一个代表玩家的 TS 客户端。

但现有 `connect(InetAddress, port)` 会把端点解析放到客户端路径；中继模式应允许由 MC 服务端解析管理员配置的目标，不能在客户端 DNS 不可用时先失败。后续需调整 transport 工厂/连接目标传递，在兼容旧实现的同时允许 targetId；不可只新增一个类却仍由 manager 走旧布尔开关。

还要把已完成的 session/routeEpoch 传给新传输的排队边界。若现有 `send(byte[])` 丢失这些元数据，应增加具有默认兼容实现的重载/数据报描述，而不是在真正发送时读取“当前 routeEpoch”给旧帧重新贴标签。具体签名在 P6 实施任务书中固定，M7 不提前改它。

### 3.2 数据路径与权限边界

```text
客户端玩家 TS 会话（密钥/身份保留在客户端）
  → Ts3Connection 已有封包/加密/发送所有权
  → TsMcChannelTransport 的有界队列
  → 当前 Minecraft 连接的 CustomPayload
  → 服务端中继会话登记表
  → 该玩家该会话独占的 connected UDP Socket
  → 管理员允许的 TS3 endpoint
```

回包逆向返回原玩家与原中继会话。服务端不解码 Opus、不混音、不成为玩家 TS 身份的持有者；这是 transport relay，不是 P7 媒体桥接。TS 登录/频道权限仍由 TS 协议会话处理。

首版仅承载已有 TS UDP 协议数据报。**TS 头像/文件传输使用的额外 TCP 数据连接不自动被覆盖**；中继握手和通话成功不能宣称所有 TS 文件功能也穿过 MC 通道。可选头像失败应独立反馈，不能让通话失败；是否扩展文件中继另行定范围。

### 3.3 建议消息与会话模型（设计草案，尚未冻结 wire）

采用独立版本的 `teamspeak-svc:ts_relay_*_v1` payload，不复用 SVC-Extra 的 ID，不把 TS 字节装入 SVC 音频消息。候选能力须能表示 TS_MC_CHANNEL 和允许的目标 ID；现有 capability enum 没有该明确语义时新增有版本约束的扩展，旧客户端不得将它误认成旧 TCP 隧道。

| 消息 | 最小内容 | 处理要求 |
|---|---|---|
| OPEN | 协议版本、requestId、targetId、purpose | 不接收任意目标 host/port；purpose 首版只批准 PLAYER_VOICE，预留 MUSIC_BOT 值但默认拒绝 |
| OPENED | requestId、不可预测 relaySessionId、连接代际、有效限制 | 服务端创建 Socket/登记成功后才回复；不是 TS 握手成功 |
| DATA_C2S / DATA_S2C | sessionId、数据报载荷、必要的流量类别/路由代际元数据 | 原 TS 数据报字节保持原样；外层有界检查；错误玩家/连接不能使用他人 ID |
| ROUTE_BARRIER | sessionId、新 routeEpoch | 与本会话数据发送顺序一致；服务端清除旧媒体队列；不修改或伪造 TS clientmove |
| CLOSE / CLOSED | sessionId、原因 | 幂等；断线可直接本地清理，不能必须等确认才释放 Socket |
| ERROR | requestId 或 sessionId、稳定错误码 | 区分目标不允许、额度、版本、连接消失、拥塞、内部失败，不映射为 TS 密码错误 |

登记键必须包含**服务端观测到的 MC 连接身份/代际 + 玩家身份 + sessionId**。不能只用玩家 UUID，也不能只信任客户端传来的 sessionId。targetId 在会话建立时绑定不可变 endpoint，后续 DATA 不携带可变目的地址。

UDP 每会话单独 Socket，绑定已批准目标并过滤其他来源回包。两个玩家、玩家语音与未来音乐 Bot 都不能共用同一 UDP 源会话。首版可限制每名玩家只一个中继会话，但协议和登记表不能写成全局单 Socket 或单个 player→socket 字段，后续开放第二会话不用推翻 wire。

状态：`CLOSED → OPENING → OPEN → CLOSING → CLOSED`；错误进入关闭流程。OPEN 只是 transport 可用，客户端 TS 会话仍需自己的握手、频道确认和音频许可。

### 3.4 资源和安全要求

- 管理员配置 targetId→允许的 TS host/port；客户端必须明确选择或授权该 TS 目标。中继拒绝任意目的 UDP 代理。私网/本机 TS 可以由管理员明确配置，不能把本项目正常的内网部署一刀切禁止。
- 服务端解析 DNS 后绑定实际目的地址，配置变化不重定向现有 Socket；重新解析/新地址按配置策略重新检查。不允许客户端通过 DATA 或“重连参数”换目标。
- 额度覆盖每连接/每玩家会话数、全服会话数、单包字节、每秒包数/字节、打开请求频率和内存队列；所有计数包括握手/控制流量，不能靠声称“控制包”绕过限制。
- 数据报上限可先以现有 4096 字节边界作为验证起点；超过上限明确拒绝，不截断后继续转发。上限须根据真实握手/分片/重连样本定案，外层在分配前检查。
- DNS、Socket 读写和等待不占 MC 主线程；Fabric 发送/接收的线程契约按目标版本验证。若必须交回主线程，调度队列也有界，不能每个数据包无限 `execute`。
- MC 断开、换后端服务器、runtime 关闭、额度撤销、超时都释放对应 Socket/worker/队列并唤醒阻塞 receive。只关闭相关 session；不能一个玩家的错误拖垮所有玩家。
- TS 端会看到中继服务端的网络来源；必须验证 TS 的连接数、同 IP 限制、反滥用策略以及管理员所允许的容量，不能承诺无限并发。
- 日志只记录 ID、状态、长度、统计和经过处理的错误；不记 TS 身份私钥、密码、票据或整包内容。

额度数值、超时和队列预算属于 P6 原型测量后的实施参数。没有测量数据时标“建议初值”，不能写成已经通过容量验收。

### 3.5 拥塞和频道隔离：需要额外注意

客户端已有 5 帧/120ms 队列可作为媒体预算参考，但中继新增的每一层都要计入总延迟；不能层层各自积压 120ms 后仍声称总体只有 120ms。

语音和命令/握手/ACK 分开有界排队；媒体过时丢弃，控制队列溢出要使该会话明确失败或背压，不能悄悄丢关键命令并继续显示已连接。服务端可以在必要时读取已定义的外层/包头类型做调度，不解密语音；客户端提交的类别不是无条件可信的额度通行证。

MC TCP 一旦已经接收字节进其发送缓冲，这些字节不能由应用单独撤回，也不能绕过前面的游戏字节。仅在应用队列里按时丢帧无法完全消除队头阻塞或已经在途的旧音频。需验证网络可写性、总排队字节和游戏网络压力；不能直接让已有 writer 的 `send` 成为无限快速向 Netty 缓冲灌数据的入口。

client/server 的 `System.nanoTime()` 不可直接跨机器相减。队列年龄先按各自本地时钟计；若要识别 TCP 在途老帧，需设计并验证有误差界限的时序机制，不能伪造绝对单向延迟。MC ping 也不等于语音端到端延迟。

routeEpoch/barrier 需要覆盖客户端队列、MC 发送提交点和服务端 UDP writer；客户端验证后再到服务端排队不等于已经发送。管理员远端移动前已发入网络的帧仍无法撤回；以可定义的本地确认边界验证，不提出物理上无法实现的零在途包承诺。

### 3.6 选择与换服规则

1. TS+AUTO 先尝试直连 UDP；只有符合既有失败分类的网络超时，才评估当前 MC 服务端已授权的 TS_MC_CHANNEL。
2. 目标必须是当前手动/自动 TS 目标的允许映射。若书签指向外部 TS 而管理员未允许它，显示“该目标不可中继”，不得改连另一个推荐 TS。
3. TS 密码、频道权限、封禁、前端不可用不通过中继重试掩盖；手动 TS 两种传输都失败时暂停，不自动改向 SVC。
4. 强制 TS_MC_CHANNEL/TCP 时，无能力/目标不允许则明确不可用；不偷偷改 UDP。
5. 从 UDP 改中继会改变服务端看到的源会话，应建立新的 TS 会话及 token、清旧队列并重新确认频道；保留用户选择、TS 身份和音量，不伪造原握手继续有效。
6. MC 换服/连接消失后该中继立即失效。保持书签意图，但标重连等待；新 MC 有允许的中继或 UDP 可用时按策略重建，不承诺无缝。不允许旧 MC payload 流入新 TS 会话。
7. 直连 UDP 的手动 TS 不因未来中继规则而变成强制跟随 MC 服务器连接。

### 3.7 P6 原型与正式验收应分开

未来可单独授权一个隔离原型：真实 MC CustomPayload 双向搬运一个客户端的 TS 原始数据报，使用固定管理员允许目标，完成 TS 握手和双向语音。原型也必须有最小包长/会话/目标/关闭限制，不能先搭建开放 UDP 代理。

正式验收再增加：两名以上玩家、错 session/旧连接拒绝、多频道、原生 TS 客户端、客户端禁 UDP 而服务端 UDP 可达、服务端 UDP 不通、DNS 条件不同、MC 大流量/弱网、客户端退出、服务端重启、跨 MC 后端切换以及所有额度。记录游戏 tick/网络负担、语音可用性、队列年龄和资源清理。

**证据门：**原型成功才固化 wire 和线程/背压实现，再编写 P6 代码任务书；原型不能直接标为 B 模式产品已完成。无 TS 插件/无独立网关是目标部署条件，需在实际环境证明。

## 4. P5：SVC_MC_CHANNEL 的兼容边界

上一轮曾按 SVC-Extra 提交 `6669d6f045e6277c640efc10ea60eff30fc9bd76` 阅读源码：其方案使用 MC CustomPayload，`svc-extra:voice` 承载 SVC NetworkMessage 原始数据，`svc-extra:config` 指定传输枚举；当时目标 MC 26.2。此处引用的是历史证据，不是对当前上游版本的新兼容承诺，见 [原架构评估](../../../review/next-stage-2026-10-28/ARCHITECTURE-ASSESSMENT.md)。

P5 的第一步是固定当前计划支持的上游提交和目标 MC/SVC 版本，逐文件核对实际 framing、socket、服务端注入、生命周期和协商。仍然要复核，而不是因历史判断重新猜“TCP 可能是独立 Socket”。

本项目自己的服务端实现随统一 teamspeak-svc 交付，要求 SVC 服务端，但不要求额外安装 SVC-Extra。与现有 Extra 服务端 wire 互操作、与 Extra 客户端双装，是两项独立承诺，分别验收。

首要技术问题是**按玩家决定 UDP/MC_CHANNEL**：原生 UDP 玩家和扩展 TCP 玩家能否在相同群组/距离范围互听。不能采用全服 transport 开关后宣称混合支持；不得用 UUID.hashCode 映射小端口空间来代替无碰撞的会话地址映射。

队列有界、close 唤醒 receive、每连接身份和 secret 关联、收发大小边界、选择期间无双发，以及 payload/Socket/DSP 唯一所有者均为验收条件。TS_MC_CHANNEL 和 SVC_MC_CHANNEL 仅复用适当的 MC 生命周期/预算工具，不共用协议 decoder 或认证状态。

在代码移植前核对来源文件和其第三方依赖的许可、保留声明及发布材料；不能把某位作者的许可表述视为覆盖全部依赖。是否可以复用具体实现以该轮源码/许可核对为准，本备忘不作重新许可结论。

## 5. 音乐系统：先明确媒体路径与控制路径

### 5.1 角色和复用边界

| 对象 | 责任 | 必须隔离的状态 |
|---|---|---|
| 玩家语音会话 | 既有 BackendCoordinator、SVC mic/PTT、TS/SVC 选择 | 不能被音乐连接重建/断开覆盖 |
| MusicSession | 明确主持端、房间、队列及自身生命周期 | 独立 session token、routeEpoch、取消与错误 |
| TS Music Bot | 独立 TS identity/client，加入明确 TS 频道并发送音乐 | 不共用玩家身份文件、UDP Socket、命令 tracker、语音 sequence、编码器 |
| MusicPlaybackEngine | 读取授权音源、解码/重采样、定时输出媒体帧 | 不采集 mic、不复用 PTT、不进入降噪/自动增益的麦克风处理链 |
| MusicSourceProvider | 元数据搜索/解析及受控音频取得 | 搜索结果不是可转播音频，凭据不随歌曲元数据分发 |
| MusicControlAdapter | 房间发现、点歌、权限、结果与状态同步 | 不能从昵称判断主持端/管理员，不让控制数据冒充媒体帧 |

这些是职责，不要求创建同等数量的空类。客户端/服务端共享的队列、权限、解码节拍与 source 契约不能依赖 Minecraft 客户端、SVC ClientApi 或 OpenAL；本地输出/GUI只在客户端适配。

Music Bot 使用独立 TS 身份和会话；玩家语音仍只有一个麦克风发送后端。音乐有自己明确授权的播放目标，不通过把文件 PCM 注入 MicRedirector 来播放。Bot 失败只关闭音乐资源，不能调用玩家 BackendCoordinator.endSession；也不能沿用 manager 的全局 current client 覆盖玩家。

Bot 不转发接收到的其他用户语音。主持人通常通过自己玩家的 TS 接收路径听 Bot，不额外本地播放同一音乐而产生双声；预览模式另行显式处理。TS 原生用户通过正常 TS 媒体接收即可听到音乐。

### 5.2 房间、权限与状态

建议模型：

```text
RoomKey = (tsServerUid, channelId, roomId)
HostBinding = (roomKey, hostTsUid, botTsUid, hostSessionId, hostEpoch)
QueueRequest = (requestId, roomKey, hostEpoch, actorUid, sourceReference)
TrackState = QUEUED → RESOLVING → PREPARING → PLAYING → FINISHED
失败终态 = FAILED / SKIPPED / CANCELLED
MusicSessionState = STOPPED / CONNECTING / ROUTE_PENDING / READY / PLAYING / PAUSED / FAILED
```

频道按 TS serverUID+cid 定位，不按 MC serverAddress 划房间；不同 MC 服务器的 TS 用户同频道共享同一音乐媒体，无需 P7。

先明确主持端，无自动选举、无离线接管。请求带唯一 requestId，重复提交不重复入队；hostEpoch 变化后旧管理员命令、旧 skip、旧状态更新不再生效。队列上限、每用户上限和点歌冷却在 Music-1 的任务书中固定，不能只创建 MusicPermissions 空接口。

权限依据当前 TS 会话中服务器提供的 sender UID/成员信息和主持端授权，不用昵称、客户端自报 role 或 MC UUID 文本。普通当前频道成员可按限额点歌；主持人能跳歌，管理员停止需来自明确配置的管理员 UID/已验证权限来源，不能先假定能读取所有 TS server group 权限。

**全频道唯一主持端需要特别定界：**没有共享仲裁者时，两个独立客户端不能只靠查看同名 Bot 就保证全局互斥。Music-1 应采用显式 owner/房间绑定、单主持端控制且不自动争抢；如果产品要求所有独立客户端在同一 TS 频道绝对排他，需要有权威主持权登记/租约及冲突策略，在实现前定案。不能把本机单例或“没发现其他 Bot”写成全网唯一证明。

### 5.3 跨 MC 点歌控制是独立需求

TS 音频能跨服传播，不代表游戏内队列控制也自然跨服。MC CustomPayload 只能到当前 MC 服务器，不能单独作为纯客户端 Music-1 的跨 MC 点歌协议。

建议 Music-1 验证**通过当前 TS 会话的定向文字控制消息**向 Bot/主持端请求：使用有版本前缀、有界内容、requestId、hostEpoch、明确房间和幂等结果；保留普通 TS 聊天，不向整个频道刷大段队列。需先核对目标 TS 协议的定向消息及通知元数据，并完成真实互操作测试，不能凭空新增 TS 原生不存在的自定义命令。

现有聊天回调若只暴露昵称和文本，必须在该轮保留可信来源 UID、clid、目标模式和 session 元数据，再做授权；不能解析用户自己写在 JSON 中的 actorUid 当凭证。若定向消息通道无法满足边界，另行决定控制方案；不能偷偷把 Music-1 改为必须装 MC 服务端扩展。

Music-3 托管服务可增加受权限控制的 MC payload 控制适配；TS 跨服控制是否同时支持需明确。两种控制适配调用相同的主持端权限/队列服务，不能各自维护一份独立队列。

### 5.4 音源、编码、播放与音量

Music-0 首个可验证音源可限定为明确授权的本地 PCM/WAV 与生成测试音；先验证流式解码、节拍、暂停/停止/资源释放，再决定 MP3/AAC/网络流所需依赖。后续加入网络音源时限制大小、持续时间/速率、重定向和资源占用；服务端抓取还要校验每次解析/重定向的目的地址，防止任意 URL 访问管理网络。本地文件引用只能由持有文件的主持端明确选取，远程点歌者不能指定任意磁盘路径。

纯 Java 共享音乐引擎不能依赖客户端 SVC 编码器的存在：Music-3 在没有 SVC 的 MC 服务端也应能用 TS 音乐能力。Opus 编码器的公共/native 实现与打包方式需在 Music-0 选定并验证服务端兼容，不能复制 SVC 私有类或假定安装 webrtc-java 就已有可用音乐编码 API。

编写时 TS 协议类已经接受 codec 4/5，并提供带 codec 的 sendVoice；这只证明有协议字段，不证明立体声音乐可以正确编码/播放。需要固定采样率、声道、帧时长、码率和 TS 频道 codec 约束，覆盖原生 TS 与扩展客户端解码。mono 与 stereo 编码/解码不能混用。不要为音乐改全局频道 codec 或提升权限，除非管理员明确允许。

按媒体时钟发送，暂停/停止不继续排入新帧；音乐积压可跳过老帧，不能挤占玩家的语音控制队列。原生 TS 频道容量与一个额外 Bot 槽位、说话权限、音乐 codec 规则需验收。

本地个人音量、音乐专用音量和自动压低只作用于该 Bot 的本地播放增益；不修改全频道发送增益。已知 Bot 的 ParticipantKey 来自可信 HostBinding，不按昵称识别。音乐本身不能触发“有人讲话”的压低检测形成自我振荡；攻击/恢复时间需平滑且可配置，保留用户现有增强偏好。

### 5.5 生命周期的推荐默认值

- 主持客户端退出 MC/退出进程时，客户端 Bot 停止；队列可保存，但不自动转交其他人。
- 玩家主动断开 TS、切换到 SVC 或关闭全部语音时，建议同时停止其本机主持的 Bot，并明确提示；不得出现玩家以为已经离开 TS 而自己的 Bot 继续隐藏发送。若希望允许独立持续音乐，须提供单独明确选项并单独确认需求。
- “关闭全部语音”至少关闭本地收听和本机音乐发送；不能因此发送命令关闭由其他人/服务器主持、给全频道服务的 Bot。
- TS_MC_CHANNEL 模式需要第二条受控 relay session；服务端尚不支持第二会话/未授权 MUSIC_BOT 时明确不可用，不抢用玩家的 relay socket。
- 音乐频道变更不得自动跟随玩家漂移扩大播放范围；默认绑定原房间，移动音乐须主持端明确操作并重新确认 Bot 频道。服务器将 Bot 移出授权房间时停止音乐。
- Music-3 服务端托管可在玩家离线后继续；MC 服务端重启/服务关闭则停止，恢复策略显式配置。客户端主持与服务器主持之间切换是权威变更，不是简单复制队列后同时播放。

以上默认值在音乐实施前作为决策确认；M7 不因此更改现有语音按钮或创建音乐开关。

SVC 共享音乐可选择直接通过合法服务端 SVC 音频接口发送，不一定要先从 TS 解码再转回 SVC；但仍是单独获准的输出后端，不能因为有 SVC 就自动开启。由同一音乐媒体源派生多个明确授权的输出时，必须防止 TS 返回路径与 SVC 注入对同一个收听端重复播放。

## 8. 交给后续实施 AI 的规则

1. 先完成明确授权的 M7，不把这份路线图当作一次性实现所有功能的命令。
2. 每一轮沿用上一轮已完成的能力，以本轮新增目标定义任务和测试；保留正确的后端、频道、session、音量标识约束。
3. 协议/装载原型和产品实现分别记录。源码、自动化、生产调用链、真实环境四列继续独立记录。
4. 后续任务书必须给出实际文件、接口、配置迁移、部署变化、失败状态、真实验收和回滚，再开始相应阶段；V3的建议类名不是要求先建空类。
5. 最终对玩家仍是 SVC+teamspeak-svc；管理员可不装，安装后按已实现功能启用。音乐、TCP、媒体桥接不得反向成为基础 TS UDP 直连的前置条件。
