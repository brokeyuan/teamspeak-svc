## P1：优先修复

### R01【已修复】：重新进服后，TS 音频继续注入已关闭的 SVC 客户端

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/TsAudioInjector.java:241-250,355-360`。
- 原因：`clientVoicechat()` 首次缓存 `ClientManager.getClient()` 后永久返回旧实例；`removeAll()`、SVC 断线和换服都不清除此缓存。
- 触发：首次正常听到 TS → 退出 MC 服务器 → 重新进入或换服。
- 影响：SVC 创建新 ClientVoicechat，但 TS 仍向旧对象送包。参考实现的 `processSoundPacket()` 在旧 connection 已置空时直接返回，因此可能显示已连接、接收计数仍增长，却一直无声，重启游戏才恢复。
- 证据：局部复现输出 `after reconnect, cached SVC client is old instance -> true`；已核对 SVC ClientManager 的 new/close 路径。
- 修复方向：按 SVC 会话更新/清空缓存，或每次取当前 ClientManager 实例。

### R02【已修复】：真实 MC 玩家被当成 Ghost 覆盖，断开 TS 时还会被删除

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/TsAudioInjector.java:185-203,303-345`；`ClientStateReflector.java:150-168`。
- 原因：`createGhost()` 对同服玩家原本不注入状态，但后续 `syncAllGhostVisibility()` 没有保留这个归属信息，直接按真实 UUID 调用 `injectGhost()`；`remove()` 同样无条件删除该 UUID 的 PlayerState。
- 触发：两个同服 mod 玩家说话后，发生任意频道成员变化；或者直接断开 TS/重连。
- 影响：真实玩家的 disabled、disconnected、group 等原始状态被新建 Ghost 状态替换，随后可从 SVC 状态表中消失，音量界面、群组列表和皮肤显示异常。
- 证据：执行原 TsAudioInjector、用状态边界替身记录操作，输出 `native -> injected`，随后 `real player state still present -> false`。真实 ClientStateReflector 的实现确实是 `states.put/remove`。
- 修复方向：明确记录状态所有权；只覆盖、删除本模块创建的虚拟状态。

### R03【已修复】：切换 SVC 私人群组时，麦克风仍向旧 TS 频道发送

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/TsVoiceManager.java:281-295,412-423`；`GroupChannelMapper.java:124-159`；`MicRedirector.java:21-36`。
- 原因：频道映射每 2 秒轮询一次，而麦克风仅检查 TS 连接是否在线，不检查当前 TS 频道是否已经对应当前 SVC 群组。等待密码和 clientmove 应答期间也继续发送。
- 触发：从公开主频道加入私人群组，立即讲话；或加入密码群组但信标尚未到达。
- 影响：切换窗口内的私人讲话会发给旧频道中的人。通常可持续到下一次映射；密码等待、命令拒绝或频道不存在时持续更久。
- 验证：调用链确认，未做游戏内复现。
- 修复方向：群组改变后暂停改道音频，直到收到 TS 当前频道已匹配目标的确认。

### R04【已修复】：密码信息缺失 6 秒后，会创建无密码频道

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/GroupChannelMapper.java:127-142`。
- 原因：`hasPassword()` 为真时只等待 6 秒；超时后将 null 密码传给 `createChannel()`。
- 触发：服务器没装配套 tsbridge，或群组信息反射失败、下发延迟/失败；该群组尚无对应 TS 频道。
- 影响：SVC 中有密码的私人群组变成 TS 中任何有加入权限的人都能进入的无密码频道。后续密码信息补到也不会给已创建的频道补设密码。
- 验证：分支路径确认，未连接真实 TS 创建频道。
- 修复方向：缺少密码时保持等待/明确报错，不能自动降低访问限制。

### R05【已修复】：同名 TS 频道覆盖缓存，可能把语音发到其他父频道

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/ts3voice/Ts3VoiceClient.java:69-72,458-465,488-502`；`GroupChannelMapper.java:134-147`。
- 原因：频道仅按小写名称键控，不按 cid 或父频道区分；后一条同名频道覆盖前一条。按父频道查询失败后，映射器又回退为全局同名频道。
- 触发：两个不同父频道下各有一个 Lobby 等同名子频道。
- 影响：即使正确子频道存在，也可能进入另一父频道的 Lobby，造成串群或讲话发给错误对象。
- 证据：真实协议类输入 parent=1/cid=10 和 parent=2/cid=20 的两条 Lobby 后，parent=1 查询返回 null，全局查询返回 20。
- 修复方向：按 cid 保存完整频道信息；以父频道+名称定位，移除越过父频道的隐式回退。

## P2：功能与稳定性

### R06【已修复】：频道删除通知没有进入处理函数，缓存永远保留旧 cid

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/ts3voice/Ts3VoiceClient.java:360-382,434-441`。
- 原因：虽然 `handleChannelRows()` 写了删除分支，但 `notifychanneldeleted cid=...` 既不包含 `channel_name=`，也不以 `cid=` 开头，入口不会调用它。
- 触发：临时群组频道因最后一人离开被删除，或管理员删频道。
- 影响：再次加入时不断向已不存在的 cid 发 clientmove，而缓存仍认为频道存在，不重建频道。
- 证据：真实协议类处理删除通知后，查询仍返回已删除的 20。
- 修复方向：显式分发频道删除事件，同时清理全部关联索引。

### R07【已修复】：clientlist 的 cid 被忽略，已在线用户频道未知

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/ts3voice/Ts3VoiceClient.java:646-680`。
- 原因：`handleClientRows()` 只读通知格式的 `ctid`，不读 clientlist 应答中的 `cid`。
- 影响：通过补拉 clientlist 才发现的用户虽有 uid/nickname，却一直没有频道信息；可见性同步会按不在频道处理，直到对方再次移动。
- 证据：输入 `clid=42 cid=7 ...` 后，`getChannelOf(42)` 返回 -1。
- 修复方向：兼容两种字段，并按快照更新频道关系。

### R08【已修复】：无 SVC 群组时，同频道 TS 用户也会被隐藏

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/TsAudioInjector.java:295-333`。
- 原因：同频道且本地没有群组时 `showGroup=null`；随后把 null 当成不可见，而不是“可见但没有群组”。
- 触发：玩家处于主频道、不加入 SVC 群组，TS 发生成员进出/移动事件。
- 影响：正在同频道讲话的 TS 用户从界面消失；下一帧又可能重新注入，形成反复显示/隐藏。
- 证据：边界替身复现 `no-group TS ghost before sync -> 1`、`after sync -> 0`。
- 修复方向：把可见性布尔值和可为空的群组 UUID 分开计算。

### R09【已修复】：服务端群组名清洗后，客户端无法映射回原 TS 频道

- 位置：`teamspeak&svcbridge/src/main/java/com/svcb/tsbridge/ts/TsChannelGroupSync.java:65-69,89-96,132-142`；客户端 `GroupChannelMapper.java:194-216`。
- 原因：服务端把 TS 名称截为 24 字符；客户端却只拿 SVC 群组名寻找频道，还会额外替换 `/\\*?`，没有保存原 cid/name 对应关系。
- 触发：TS 频道名超过 24 字符，或包含客户端会改写的字符。例如 `123456789012345678901234X`、`Raid/One`。
- 影响：加入镜像群组时找不到原频道，创建第二个频道；长名称还可能被两个频道截成同一个群组名。
- 验证：双方名称变换及查找路径确认。
- 修复方向：下发稳定的 TS cid 映射，不用清洗后的显示名反查目标。

### R10【已修复】：ServerQuery 登录失败时泄漏新建的连接

- 位置：`teamspeak&svcbridge/src/main/java/com/svcb/tsbridge/ts/TsQueryClient.java:78-96,106-118`。
- 原因：新建的 `newQuery` 直到 login/selectVirtualServer/setNickname 全成功后才赋给 `this.query`；任一步失败，catch 内的 `disconnect()` 只能看到 null/旧字段，无法关闭 newQuery。
- 触发：密码错误、虚拟服务器端口错误、设置昵称失败并持续重试。
- 影响：每次重试可能留下 socket 和库线程，长期运行累积资源。
- 验证：资源所有权与异常路径确认，未向真实 ServerQuery 注入登录失败。
- 修复方向：用局部 finally 关闭未成功提交的新连接。

### R11【已修复】：玩家离线与连接成功竞态，可留下无人管理的 TS 镜像

- 位置：`teamspeak&svcbridge/src/main/java/com/svcb/tsbridge/transport/PlayerVoiceClients.java:98-112,203-210,258-286`。
- 原因：离线流程先令 online=false 并清理 `pc.client`；正在 connect 的线程可能在清理后才赋值 `pc.client`，随后发现离线直接 return，没有 finally 再清理新连接。
- 触发：玩家退出恰好发生在握手成功、引用提交前后。
- 影响：玩家已离线，但其 TS 客户端和底层收发线程仍在线；players 表已移除此条，后续对账也找不到它。
- 验证：并发交错路径确认，未用真实握手压测复现。
- 修复方向：提交连接前复核会话代际/在线状态；拒绝提交时显式 disconnect，退出循环用 finally 清理。

### R12【已修复】：关闭 TCP 隧道只关闭监听，现有隧道仍继续转发

- 位置：`teamspeak&svcbridge/src/main/java/com/svcb/tsbridge/net/TcpTunnelServer.java:53-65,104-120`。
- 原因：stop 不追踪、关闭已接受的 TCP/UDP socket；serve 的两个循环也不检查 running。
- 触发：已建立隧道后关闭模块/MC 服务器。
- 影响：只要对端继续发包，旧连接就能继续转发并保留两个线程；同 JVM 重新启动时还可能存在旧连接。
- 证据：本机 TCP/UDP 实测，stop 后 `isRunning=false`，现有连接仍能双向转发。
- 修复方向：维护活动会话集合，在 stop 中关闭所有会话的两侧 socket。

### R13【已修复】：桥接群组过滤查询失败时，所有玩家语音被允许外发

- 位置：`teamspeak&svcbridge/src/main/java/com/svcb/tsbridge/svc/McToTsDispatcher.java:46-53`；`ghost/GhostPlayerInjector.java:175-210`。
- 原因：成员读取失败返回 null，调用方只在 members 非 null 时排除非成员。
- 触发：SVC 内部反射不兼容、服务尚未就绪或读取状态异常。
- 影响：本来不属于桥接群组的普通聊天/其他私人群组语音会进入 TS。另有 1 秒成员缓存，离开桥接群组后不能立即撤销外发资格。
- 验证：异常返回值到转发路径确认。
- 修复方向：无法确认群组权限时拒绝外发；成员变化使授权缓存立即失效。

### R14【已修复】：reload 修改运行模式，但旧组件不停止、新组件不启动

- 位置：`teamspeak&svcbridge/src/main/java/com/svcb/tsbridge/command/TsBridgeCommands.java:213-230`；`config/BridgeConfig.java:144-148`；`TsBridgeMod.java:184-202,352-354`。
- 原因：reload 只逐字段替换配置，没有重建运行时；维护任务和新进服信标却立即采用新的 mode、host、tunnelPort 等值。
- 触发：运行中把 bridge 改为 group-sync，或反向修改；改变隧道端口。
- 影响：新客户端按 direct 连接，但旧服务端音频桥和玩家镜像仍在；反向切换则客户端休眠而服务端并未启动桥。信标也可能公布尚未监听的隧道端口。
- 验证：命令到组件生命周期路径确认。
- 修复方向：定义支持热更新的字段；需重建的字段统一停止/重启，或明确拒绝并要求重启。

### R15【已修复】：默认构建入口在当前项目目录不可用，服务端 wrapper 路径也不完整

- 位置：两个模块的 `gradlew.bat:36-43`；服务端 `gradlew.bat:74` 及目录结构。
- 原因：批处理 `set DIRNAME=%~dp0` 等赋值未加引号，当前目录名包含 `&`，被 cmd 拆成两条命令。服务端另把 wrapper jar/properties 放在模块根目录，脚本却引用 `gradle/wrapper/gradle-wrapper.jar`。
- 影响：按 README 执行 gradlew.bat build 直接失败；仅处理路径转义仍不能解决服务端 jar 位置不符。
- 证据：两模块实际启动都报路径被拆分；直接调用服务端脚本期望的 jar 也报 Unable to access jarfile。
- 修复方向：使用完整标准 wrapper 目录和正确的批处理引用方式，并在含空格、& 的目录验证。

### R16【已修复】：界面声明支持主频道密码，实际只把它当服务器密码发送

- 位置：`teamspeak-svc/src/main/java/com/tsvoice/client/ServerConfigStore.java:35-36`；`TsVoiceManager.java:353-354`；`GroupChannelMapper.java:115-116,157-158`；`ts3voice/Ts3VoiceClient.java:634-636`。
- 原因：配置密码写入 `client_server_password`，`client_default_channel_password` 固定空；没有群组时映射器进主频道用的 groupPassword 也是 null。
- 触发：TS 主频道设有频道密码，玩家在界面填入该密码并尝试连接。
- 影响：无法按文档/字段说明进入受保护主频道；连接状态可能显示成功，但 clientmove 一直被拒绝。
- 验证：配置到 clientinit/clientmove 的参数流确认，未对真实密码频道复现。
- 修复方向：把服务器密码和频道密码拆成不同字段，并在对应协议操作中使用。
