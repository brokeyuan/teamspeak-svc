## D01：总体部署与产品边界

**问题**：TS/SVC 全部连接是否强制经过一个中心服务？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 客户端直连 + 可选服务 | 手动 TS/原版 SVC 可独立工作；与现有协议接近；服务可逐个交付 | 需要 SVC 内部前端适配，兼容测试较多 |
| 全部走中心网关 | 后续 WebRTC/账号/房间更集中 | 强制运维依赖、额外链路与信任边界；不自然支持任意 TS 书签 |
| 所有模式依赖 SVC 服务端会话 | 改动小 | 无 SVC 时手动 TS 不可用，不满足最终需求 |

**推荐**：客户端直连为主；能力公告、TS 隧道、SVC 媒体网关按需部署，可同包但独立启停。旧桥不是强制依赖。

**理由**：满足当前任务书全部方向且可逐阶段验证；不为了远期浏览器先改变所有通话部署。

**是否阻塞**：阻塞 P1 后端协调器的产品边界；P0 确定缺陷修复在获实施批准后可独立进行。

## D02：无 SVC 服务端时的前端适配与版本范围

**问题**：为了复用 SVC 采集/播放/GUI，接受多大内部 API 依赖？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 固定目标版的有限 Mixin/内部适配 | 保留原版体验，客户端可独立 TS | 需 pin 实际 ABI、启动自检、真实设备回归 |
| 等待/推动 SVC 增加独立前端 API | 长期维护更清晰 | 上游排期和接口尚不确定，不能据此承诺交付时间 |
| 自制完整音频前端/GUI | 完全自主 | 高维护成本，与不重做 GUI 的目标冲突 |

**推荐**：先验证 MC 26.3 + SVC 2.6.25 的有限适配，封装于 Svc2625FrontendAdapter；同时记录可提交上游的最小扩展点。关键 hook 不可用时明确禁用 TS，未接管时原版 SVC 可继续用。

**已证实约束**：实际 SVC JAR 无 connection 时 processSoundPacket 返回；AudioChannel 构造器与 26.2 参考源码不同。独立 mic/playback 的真实通话尚未验证。

**是否阻塞**：阻塞 P2 的正式支持范围和“无 SVC 服务端”发布承诺；纯策略/模型工作可先行。P2 验证失败必须回来决策，不能自行强制增加服务端。

## D03：TS 频道与原版群组界面的关系

**问题**：TS 频道是否必须完全复用原版 SVC 群组数据和动作？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 原版入口旁提供 TS 子页，SVC 模式原页保留 | 改动有限；权限、频道树可真实表达；无需重做整体 GUI | TS 模式多一个子页 |
| 将原群组列表数据源/动作切成 TS | 操作外观最接近 | GUI/Mixin 接触面更大；NORMAL/ISOLATED/OPEN 与 TS ACL 不等价 |
| 完全镜像所有 TS 频道成 SVC 服务端群组 | SVC 原页可见 | 需要可选服务端也被变成必需；密码、冲突和权限维护复杂 |

**推荐**：TS 子页 + 复用原版列表风格、返回习惯和个人音量；有需要再做受限的原群组页数据源适配。legacy GroupChannelMapper 作为明确模式保留，手动 TS 频道选择不受其周期覆盖。

**理由**：无 SVC 服务端时不存在可由原版服务器确认的 SVC 群组，不能把本地伪群组当真实服务端群组。

**是否阻塞**：阻塞 P3 频道 UI 范围；不阻塞书签数据模型或请求关联。

## D04：自动回退能否改变语音网络

**问题**：TS 失败时，什么时候可以把玩家转到 SVC？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| AUTO 允许有通知的受控回退；手动 TS 默认不跨后端 | 符合默认可用与手动意图；避免错误受众 | 状态和发言边界实现较复杂 |
| 每次跨后端都确认 | 受众选择最明确 | 用户操作更多，影响自动恢复 |
| 失败立即自动送另一后端 | 自动化最简单 | 持续 PTT 会把同一段话送给另一群人，不接受作为默认 |

**推荐**：AUTO 首次可按明确展示的本服策略自动选 SVC；运行中失效先静音并通知，仅在策略允许与发言边界后切换。PINNED_TS 默认只重试同 TS/兼容传输，提供显式“改用本服 SVC”。切换后不自动抢回上一个网络。认证/权限错误不通过改传输或改后端掩盖。

**理由**：传输可用性和谈话受众是不同问题；当前瞬时 isConnected 放行路径已复现异常泄漏条件。

**是否阻塞**：阻塞 P4 默认策略与 UI 文案；不阻塞 P0/P1 先保证失败关闭发送。

## D05：换 MC 服务器和退出世界时，手动 TS 如何处理

**问题**：TS 会话要跟随 MC 世界生命周期到什么程度？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 换服保持显式 TS 目标；世界外暂停音频 | 跨服体验连续，避免主菜单意外收发 | 前端 lease 随世界切换，连接与音频状态分离 |
| 每次换服断开 TS | 实现较简单 | 手动书签受 MC 过度影响 |
| 主菜单继续完整通话 | 更接近独立 TS 客户端 | 设备、隐私、GUI和失焦行为需额外产品设计 |

**推荐**：换服不改显式目标/TS 连接；MC context 与可选身份单独更新。世界外默认暂停采集/播放，网络保留与否由连接资源测试决定；未来另提供明确的后台通话开关。

**理由**：满足不必要耦合的解除，同时不默认为独立后台语音客户端。

**是否阻塞**：阻塞 P2 生命周期真实验收；不阻塞 TS 网络会话去耦。

## D06：SVC-Extra 的兼容承诺和双装策略

**问题**：支持 wire 兼容、现成客户端双装，还是维护一个目标版移植？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 单装客户端 wire 兼容，双装限定已测版本 | 控制 Socket/DSP 所有者；可逐步交付 | 需清楚列出不支持版本 |
| 要求 Extra 提供网络/DSP 集成接口或共同维护移植 | 双装维护较清晰 | 需要上游协作，不能假定对方会提供 |
| 任意版本双装都尽力覆盖 | 宣传范围大 | ID 重复注册、final socket 覆盖、双重 DSP/native 冲突不可控 |

**推荐**：先支持固定提交 wire，客户端不装 Extra 时本项目拥有 MC_CHANNEL；双装通过受版本约束的桥接接口，默认由 Extra 拥有相交 DSP。无桥时关闭本项目 D 自动接管，清晰说明能力。目标 26.3 兼容版未取得前不承诺双装。

**已证实约束**：上游快照目标 MC 26.2；config 只有枚举、没有完整协商；服务端 transport 是全局选择，不能假定可与 UDP 原版玩家混用。

**是否阻塞**：阻塞 P5 的双装与目标版本支持范围；不阻塞 A/C/书签，也不阻塞为 wire 写 golden tests。

## D07：TS TCP 隧道的授权和部署

**问题**：B 是保留旧桥私有隧道，还是独立服务；如何认证普通书签用户？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 独立 TLS 服务 + 每用户凭据/短时票据 | 不依赖 MC；根秘密不发玩家；独立运维 | 需要凭据发放、证书、撤销和限额管理 |
| 经 MC 服务端发短时票据 | 本服玩家操作少 | 只能覆盖该 MC 部署，不满足任意手动书签 |
| 所有人配置同一个 HMAC 根秘密 | 延用 v1 最简单 | 所有客户端可自行签票，不能做细粒度授权；本身不加密 |

**推荐**：独立 TLS v2 + 每用户 gateway credential，MC 代取票据为可选便利；v1 仅显式受控兼容。gateway endpoint 与 TS endpoint 分开，不允许任意目标转发。v2 不能协商失败后偷偷降级 v1。

**未证实事项**：现有真实公网/反向代理部署、TLS 证书运维方式和用户凭据提供者尚未给定；不能写成已有服务。

**是否阻塞**：阻塞 P6 的认证接口/公开部署；可先做核心传输注入和 v1 故障回归。

## D08：互通网关 MVP 的语音范围

**问题**：普通 SVC 与 TS 首期互通到什么程度？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 显式 SVC 桥接群组 ↔ 固定 TS 频道 | 授权/受众清楚，易回归与停用 | 需要玩家加入该组，不包含所有距离语音 |
| 所有距离语音直接转 TS | 看似无操作 | TS 频道不能自然保持 SVC 各听者的距离范围，容易扩大受众 |
| 多群组/全频道动态映射 | 灵活 | 路由/权限/密码/跨服环路复杂，宜后续独立项目 |

**推荐**：单群组单频道，默认关闭、管理员显式启用；音频不依赖身份配对。先完成 P0/P1 的受众/路由保护再迁移旧桥代码。

首期进一步限定为单媒体网关；跨 MC 的客户端直连 TS 仍正常支持。多个 MC 服务端的普通 SVC 玩家都经各自网关接同 TS 时，需要另行批准多网关扩展，并按实施计划的方向表区分本地出口（屏蔽回注）与远端出口（仅下行到本地 SVC）。不能用一份“屏蔽全部网关 UID”名单替代路由设计。

**理由**：最低可用的真正互通，保留其他 SVC 玩家的原版范围和隐私预期。

**是否阻塞**：阻塞 P7 的路由模型/验收范围；不阻塞直连客户端。

## D09：TS 网关代表一个群体还是每个玩家

**问题**：网关 MVP 用单 bot 还是 per-player 镜像？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 单 bot/每桥接房间一个 bot | 少量槽位/身份/连接；多人混音模型已有 | TS 看见的是桥接房间，权限为 bot 权限；需要混音 |
| 每玩家独立 TS 客户端 | TS 名单可辨别玩家；可规划每人 ACL | 消耗槽位、线程、带宽和身份管理；需加入意愿与配额 |
| 两种都默认启用自动选择 | 自动化多 | 路由重复/回声/故障分支大，不利首期稳定 |

**推荐**：单 bot 先验证完整互通，per-player 后续开关；若开发者把 TS 原生逐玩家名单与权限作为 MVP 必需，应改为 per-player 并单独批准容量/身份托管方案。

**理由**：普通玩家直连 TS 已提供逐用户体验，网关首期优先让原版 SVC 用户可靠互听；不能把 bot 权限描述成玩家 TS 权限。

**是否阻塞**：阻塞 P7 音频/容量与权限契约；不阻塞抽取纯协议算法。

## D10：MC↔TS 身份信任来自哪里

**问题**：哪个主体有权把 TS UID 映射为可信 MC UUID？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 本地显式 pin issuer，或管理员维护联盟目录 | 信任范围可解释，可撤销/审计 | 玩家/管理员需分发信任；跨服目录尚未建设 |
| 当前 MC 服务器自签即全局可信 | 部署简单 | 任意 MC 服可宣称其他 UUID，越过全局身份边界 |
| 全部只作未验证 Ghost | 最少信任/依赖，语音照常 | 暂无可信跨服皮肤/真实玩家关联 |

**推荐**：默认未验证 Ghost；有本地 pin/明确联盟策略再提升展示身份，加入 expiry/revision/tombstone。当前 MC 连接只能建立来源上下文，不能自动获得全局担保；昵称/description/公开配对码不算证明。声称绑定 MC UUID 时区分服务器管理的离线 UUID与经过外部认证的账号身份。

**已证实缺陷**：当前 ClientIdentityService 保存 expiry=now，且未使用本地信任目录；修 expiry 时必须同步接信任规则。现有服务端声明分发只覆盖当前 MC 连接，不能承诺跨服互认。

**技术约定**：持久 issuer 的 revision 跨重启单调，先原子保存再签发/撤销；客户端保存高水位和撤销墓碑。现有签发端 AtomicLong(1) 必须同步迁移。实施计划采用最大声明 TTL 24h、偏差 60s 的初始策略；未来改变 TTL 时同步延长墓碑保留期，不可提前清除旧声明的防重放保护。

**是否阻塞**：阻塞 P0 身份提升的具体策略；安全默认为 Ghost 可先明确，整个音频路线不应被身份目录阻塞。

## D11：首发范围、质量门与可测环境

**问题**：四模式、网关和未来平台是否必须一次发布？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| A/C 核心体验先发，再分别 D/B/网关 | 每个切片可真实验收，风险集中 | 分多次发布，须清楚区分已支持与规划 |
| 四模式及网关一次发布 | 宣传完整 | 涉及 Extra 移植、隧道运维、设备/TS/MC 多实例，验收面大 |
| 只编译和替身回归后发布全部 | 最快 | 不足以证明功能，任务书明确不接受 |

**推荐**：P0–P4 为第一切片，P5/P6 分别交付 D/B，P7 单独可选网关；每次执行 P8 对应真实矩阵。30 分钟长流/回绕、设备/静音/权限、断线/切换、无双发/回声、关闭资源基线必须有证据。

**待确认**：实际可提供的 TS3 服务端版本、MC 客户端/服务端实例、OS/设备、兼容 Extra 目标版与 UDP/TCP 故障注入条件。音频 p99 和端到端延迟门槛以基线实测细化，不把未经测量数值当承诺。

**是否阻塞**：阻塞公开发布与“已支持”标记，不阻塞方案文档或确定性离线测试。

## D12：共享模块、旧桥与来源管理

**问题**：是否立即把两套 TS 栈全部并入 ts3voice-core，以及如何处理旧桥？

| 选项 | 优点 | 代价/约束 |
|---|---|---|
| 分阶段抽共享纯协议，旧桥可独立保留 | 防漂移、范围可回滚；客户端不强制旧桥 | 过渡期仍有副本，需差异检查与同步向量 |
| 一次性合并全部 TS/业务/GUI | 看似结构统一 | 会把不同生命周期和协议适配混到一起，回归风险高 |
| 永远维持整栈双副本 | 当前改动少 | 安全/序号/协议修复继续漂移 |

**推荐**：保留 core 已共享算法和 wire；P1 先抽 Transport/Listener 的必要边界，P7 再按实际网关需求迁移纯 TS 栈。MC/Fabric/GUI/DSP 不进入 core。旧公告/群组/隧道 v1 显式适配；TS3AudioBot HTTP fallback 不作为新项目默认依赖，只有现有用户确有部署需要时单独保留适配器。

**来源约束**：实际移植文件的上游版权/许可证和重新分发边界须逐项核对；当前 notices 不足以证明所有协议文件均可按现有标签重新许可。不要为统一许可自行删来源头或改许可证。

**是否阻塞**：阻塞新共享协议包公开分发/重新许可和旧桥淘汰动作；不阻塞本次保留源码、读取和设计，也不需要先删除任何旧文件。

## 确认顺序与最小审核输入

建议开发者先确认 D01、D02、D04、D05、D10，随后确认 P3 UI/配置（D03）；决定实施 D/B/网关切片时再确认 D06–D09。D11/D12 在对应发布前收口。

若只批准第一切片，实施者仅做 P0–P4 与相关 P8；新隧道/网关/Extra 双装仍是规划，不擅自扩范围。若拒绝推荐，可更新这三份文档的接口/验收/依赖后再实施，不能让第三个 AI 自行猜测产品取舍。
