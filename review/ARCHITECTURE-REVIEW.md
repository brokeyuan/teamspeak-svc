# teamspeak-svc 架构审查与重构建议

> **审查对象**：`teamspeak-svc.zip`（版本 0.9.8）  
> **审查角色**：Java 架构、网络协议、实时音频与 Minecraft Fabric 模组工程审查  
> **审查方式**：基于此前完成的静态源码、配置与历史日志审查结果整理。**未在本次文档整理中重新运行 Gradle 构建、Minecraft 集成测试或性能基准测试**。  
> **总体判断**：建议完成关键修复后再作为稳定版本发布。

## 1. 执行摘要

项目的整体技术路线合理：保留 Simple Voice Chat（SVC）的交互界面，通过独立 TS3 客户端实现语音传输，同时集成群组映射、Ghost 玩家、回声消除、降噪和混响。

当前主要工程风险不是 Java 语法或单纯的类规模，而是**网络会话、SVC 内部状态和音频处理三个生命周期耦合**，同时又由不同线程驱动。这类问题可能在长时间运行、切换服务器、频繁重连、丢包及修改音频配置时暴露。

优先事项：

1. 确保麦克风转发失败时不会意外恢复原始 SVC 语音发送。
2. 修复 TS3 命令序号回绕和接收窗口处理。
3. 隔离旧 TS 会话的迟到回调，防止错误解释语音数据。
4. 修复文件上传确认与头像缓存作用域。
5. 将实时音频热路径中的不必要分配、锁竞争和全量状态更新移出或优化。
6. 用明确的会话对象和最小职责接口逐步替代全局静态状态。

## 3. 核心逻辑与正确性问题

### 3.1 [P0] 麦克风改道失败可能回落到原始 SVC 发送

**位置**：`MicRedirector.java:21–40`

此前审查提取的关键逻辑：

```java
byte[] opus = encoder().encode(pcm);
if (opus != null && opus.length > 0
        && TsVoiceManager.sendMic(opus)) {
    event.cancel();
}
```

**问题**：`event.cancel()` 仅在编码成功且 TS3 接受帧后调用。若 TS3 已接管语音发送，但编码器失败、抛出异常或输出空帧，原始 SVC 事件可能继续执行，与“连接 TS 时不经 MC 服务器转发语音”的预期不一致。

**改进建议**：

- 将“当前模式是否接管 SVC 原始发送”与“本帧是否成功通过 TS3 发送”解耦。
- 明确接管状态下的失败语义：失败应丢帧、记录指标并尝试恢复，不应悄然使用另一条发送路径。
- 增加编码失败、空帧、发送失败、连接瞬断时的回归测试。
- 检查事件回调异常处理是否仍能保证必要的原始发送抑制。

**验收标准**：TS 接管模式下，无论单帧编码或发送成功与否，都不会意外经原始 SVC 通道发送语音。

### 3.2 [P1] TS3 命令序号回绕处理不完整

**位置**：`Ts3Connection.java:449–535`

```java
int id = base;
// ...
id++;
base = id;
```

**问题**：TS3 包序号在线路层为 16 位，`65535` 后应回绕为 `0`。如果重组队列直接递增整数并等待不存在的 `65536`，可能造成命令组装或后续处理停滞。这里还需要确保乱序、重复包和跨回绕分片均正确处理。

**改进建议**：

- 将线路层 16 位序号与应用层扩展序号明确区分。
- 对接收窗口建立一致的回绕、窗口推进和去重策略。
- 把命令组装抽取为不依赖 Minecraft 的纯 Java 组件。
- 添加 `65534 → 65535 → 0 → 1`、跨回绕乱序、丢包、重复包及分片测试。

**验收标准**：回绕边界前后仍能持续正确重组并处理控制命令。

### 3.3 [P1] 旧会话回调可能错误关联到新会话

**位置**：`TsVoiceManager.java:359–363、521–542`

现有绑定方式：

```java
c.setVoiceListener(TsVoiceManager::handleVoiceFrame);
```

**问题**：如果处理回调时读取的是静态当前 `client`，旧连接的迟到语音帧可能被新连接的客户端目录解释。切服、重连和线程交错时尤其容易出现竞态。

**改进建议**：

```java
c.setVoiceListener(frame -> handleVoiceFrame(c, frame));
```

- 将来源连接实例与回调绑定。
- 使用 `SessionContext` 或 `sessionGeneration` 标识连接代际。
- 处理帧前核对回调归属；旧会话数据直接丢弃。
- 在断开连接时撤销或失效化旧会话回调，并测试快速重连。

**验收标准**：旧连接的语音帧永不注入新会话，也不能污染新的身份映射。

### 3.4 [P1] 未支持的音频编码仍可能继续注入

**位置**：`TsAudioInjector.java:99–110`

**问题**：当 `codec` 不是受支持的 Opus Voice / Opus Music 类型时，当前代码可能只记录警告，仍向 SVC 注入数据。

**改进建议**：在不支持的编码分支明确 `return` 或采取与协议一致的拒绝行为；记录可诊断的错误但避免每帧刷日志。

**验收标准**：不支持的音频数据不会被交给 Opus 解码路径。

### 3.5 [P1] 文件传输完成判定不可靠

**位置**：`Ts3FileTransfer.java:60–88`

**问题**：写入数据之后仅执行一次 `read()`，随即返回成功，不能充分证明服务端接受并持久化了文件。另外，源码注释对于超时可视为提交完成的描述，与实际通过异常路径返回 `false` 的行为不一致。

**改进建议**：

- 明确区分 `SENT`（本地写出）、`CONFIRMED`（服务端确认）、`UNKNOWN`（超时或连接中断）、`FAILED`（明确失败）。
- 根据 TS3 文件传输协议完整检查结果，而非依赖一次读取。
- `UNKNOWN` 不应直接写入永久成功标记；必要时通过后续查询确认。
- 用模拟短读、超时、服务端关闭及拒绝上传的测试覆盖。

### 3.6 [P1] 头像上传缓存未按服务器隔离

**位置**：`AvatarPipeline.java:39–67、145–148`

现有完成标记形如：

```text
avatar_<UUID>.done
```

**问题**：标记只与 Minecraft UUID 关联。上传到 TS 服务器 A 后，换到 TS 服务器 B 可能错误跳过上传。

**改进建议**：缓存键至少覆盖 TS 服务器身份、TS 客户端 UID 与 MC UUID；同时提供失败重试、手动刷新和缓存失效策略。

**验收标准**：服务器切换后不会错误复用其他服务器的上传结果。

## 4. SOLID 与模块边界

### 4.1 单一职责原则（SRP）

**现状**：`TsVoiceManager`（此前统计约 543 行）负责配置解析、会话状态、线程启动、重连、身份加载、频道文字和语音发送。`Ts3VoiceClient`（约 882 行）同时承担握手、目录、命令处理和回调等职责。

**建议拆分**：

| 新组件 | 核心职责 |
| --- | --- |
| `VoiceSessionCoordinator` | 会话级协调与对外入口 |
| `SessionConfigResolver` | 解析信标和本地配置 |
| `TsConnectionSupervisor` | 建连、关闭、超时与退避重试 |
| `VoiceFrameRouter` | 语音发送、接收和会话隔离 |
| `TsIdentityRepository` | TS 身份读取、保存与更新 |
| `Ts3CommandAssembler` | TS 命令组包、乱序与回绕 |
| `Ts3ChannelDirectory` | 频道目录和查找 |
| `Ts3ClientDirectory` | 客户端目录和身份映射 |

重点不是机械拆文件，而是确立**状态归属、生命周期和线程边界**。

### 4.2 开闭原则（OCP）与依赖倒置原则（DIP）

**现状**：`AudioPipeline` 使用枚举和分支判断选择 WebRTC 或 NVIDIA 降噪，实现新的处理器需要修改核心分发逻辑。

**建议**：

```java
public interface AudioProcessor extends AutoCloseable {
    void process(short[] pcm);

    @Override
    void close();
}
```

- 引入 `AudioProcessorFactory` 处理不同实现的创建和可用性判断。
- 将处理器初始化与实时音频回调解耦。
- 将配置生命周期与资源清理纳入明确定义的 `SessionContext` / `AudioRuntimeContext`。

上述接口仅为架构方向示例，最终缓冲形态需结合音频帧格式、长度和零分配要求确定。

### 4.3 接口隔离原则（ISP）

**建议**：上层分别依赖最小化的语音传输、频道管理、文字通信和文件传输接口，避免单个巨型 TS 客户端接口使 GUI、音频、上传等模块相互牵连。

### 4.4 可替换性与兼容边界（LSP / 实际工程约束）

对第三方 SVC 内部状态和原生 DSP 的适配应封装在适配层，而不让业务逻辑直接假定反射对象结构或某一种原生库永久可用。引入新实现后应保持相同的成功、失败、关闭语义。

## 5. 重复代码、可读性与维护性

### 5.1 配置刷新流程重复

**现状**：`AudioExtraScreen` 等入口重复执行配置保存、`TsAudio` 刷新、`AudioPipeline` 重建和连接管理器通知。

**建议**：建立 `ConfigApplyService`，对新旧配置做差异比较，按影响范围分别触发：

- 仅更新运行时参数；
- 重建指定 DSP；
- 重启音频处理链；
- 重建网络会话。

避免每次 GUI 操作都重复触发整条链路。

### 5.2 反射字段与异常吞没

**位置**：`AudioExtraScreen`

**问题**：使用反射按字段名修改配置、异常后直接忽略，会使配置保存失败难以排查。

**建议**：使用类型安全的绑定或显式访问器；错误进入统一状态通道，必要时在 UI 提示。

### 5.3 使用字符串查找解析 JSON

**位置**：`AvatarPipeline.extractValue()`

**建议**：使用项目已有 Gson 解析结构化 JSON，避免空格、转义和字段组织变化造成误读。

### 5.4 超长原生接口绑定文件

**位置**：`NvAudioEffects.java`（此前统计约 1,354 行）

**建议**：若为原生绑定/生成代码，单独管理，标明来源与生成方式。**不应为了行数好看而手动拆改生成代码**，以免影响 ABI 一致性。

### 5.5 关键 Mixin 静默失效

**位置**：`teamspeak-svc.mixins.json`

`defaultRequire: 0` 有兼容性价值，但也会让关键注入可能静默失败。

**建议**：启动时执行核心能力检测，显示具体未生效的功能；不要仅靠“没有崩溃”推定音频改道成功。

## 6. 性能与实时性

| 优先级 | 文件 / 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| P1 | `WebRtcNative.java:50–68` | 每个 10 ms 块创建字节数组及缓冲视图 | 预分配并复用工作缓冲 |
| P1 | `AudioPipeline.java:165` | 实时处理和初始化/重配置共享类锁 | 初始化离开热路径，测量锁等待 |
| P1 | `GroupChannelMapper.java:34–49` | 每帧可能遍历频道表 | 缓存已确认路由，仅在状态变化时重算 |
| P2 | `ClientStateReflector.java:129–166` | Ghost 可见后仍重复覆盖 PlayerState | 差异更新 |
| P2 | `OnlinePlayers.java:24–39` | 每 Tick 重建 Map / Set | 事件驱动更新或不可变快照 |
| P2 | `AecReferenceMixer.java:20–27` | 入队分配 `short[480]`，通过 `queue.size()` 控容量 | 使用有界环形缓冲 |
| P2 | `RayTracedReverb.java` | 600 条射线、最多 5 次反弹 | 建立性能预算，动态降低采样量 |

**性能验证**：分别记录正常语音、多人同时说话、弱网、频繁切服和设置修改时的 CPU、分配速率、GC 暂停、帧处理 P50/P95/P99 耗时，以及超过帧预算的次数。不要只凭平均 CPU 判断音频实时性。

## 7. 用户体验优化

| 场景 | 可能的体验问题 | 推荐改进 |
| --- | --- | --- |
| TS 连接失败 | 无法分辨失败来源 | 区分 DNS、认证、超时、权限错误 |
| 自动重连 | 状态不透明 | 显示当前阶段与下一次重试状态 |
| 群组切换 | 路由待确认时麦克风暂停 | 明确提示“正在切换频道，麦克风暂时暂停发送” |
| NVIDIA 降噪不可用 | 诊断不足 | 指出 DLL、初始化或模型加载原因 |
| 地址和端口 | 无效端口可能静默回退 9987 | 校验 `1–65535`，阻止无效提交 |
| 信标自动连接 | 服务器引导连接外部地址 | 首次信任新目标时明确展示目的地 |
| 头像上传 | 上传状态不可辨 | 显示成功、拒绝、失败及重试入口 |
| 音频设置 | 启用后难验证 | 提供短时本地麦克风试听与处理状态 |

### 7.1 Ghost / 玩家身份可信度

**现状**：`Ts3VoiceClient` 从 `client_description` 读取 `tsvc-uuid`，`TsVoiceManager` 还可根据 `[MC]` 昵称匹配在线玩家。

**风险**：昵称及客户端描述属于可被伪造或修改的信息，不宜单独认定为已验证的 Minecraft 身份。

**建议**：区分“未经验证的外观映射”和“可信身份映射”；对于带皮肤与玩家身份暗示的 GUI，避免将未认证信息呈现为可靠事实。

## 8. 构建、依赖与交付

### 8.1 macOS x86_64 原生库缺口

`WebRtcNative.java` 包含 macOS x86_64 路径，但 `build.gradle` 未声明对应的 `macos-x86_64` classifier。应补齐依赖并验证，或明确列为不支持的平台。

### 8.2 自动化测试布局

目前缺少标准 `src/test` 目录；部分协议测试位于 `src/main`，发布时通过 `jar.exclude` 排除。

建议建立可由 CI 执行的 JUnit 测试，覆盖：

- TS 命令序号回绕、乱序和分片。
- 重连后的旧会话数据隔离。
- SVC 麦克风拦截失败路径。
- 配置变更与资源释放。
- 文件传输明确失败、未知和确认成功。
- 头像缓存跨服务器切换。
- Ghost 身份映射的冲突、失效与伪造输入。

### 8.3 归档体积与许可证

此前 ZIP 约 142 MB，其中包含较多 `.gradle/` 与 `build/` 内容。源码发布包应排除缓存和编译产物；README 声明 GPL-3.0，但归档根目录未看到完整 `LICENSE` 文件，正式发布前建议核查许可证文本及移植代码授权。

## 11. 最终结论

项目已经具备 TS3 协议握手、身份、命令重发、频道操作和音频收发等核心能力，没有必要全面重写。下一步最值得投入的是：

1. 解决真实影响业务正确性的发送回退、序号回绕和跨会话竞态。
2. 给重要状态建立**单一所有者**及明确的创建、停止、清理机制。
3. 对实时音频路径执行可重复的性能测量。
4. 以自动化协议和回归测试支撑重构。

**架构重构的标准不是减少行数，而是让职责、状态和生命周期都能够清晰归属、独立验证、可靠恢复。**
